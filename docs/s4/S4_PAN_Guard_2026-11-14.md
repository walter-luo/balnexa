# Payment-card number guard (D-PAN-1, migration 9041)

`DRAFT — AI-generated` (the author: Claude). Branch `s4/pan-guard` (stacked on `s4/null-guard-sweep`), migration **9041**, release **0.9.7-p2**. Synthetic data only: the tests build their card numbers at run time, and no card number literal is committed.

## Decision

| ID | Decision | Grade | Reason |
|---|---|---|---|
| D-PAN-1 | A full payment-card number (PAN) is never stored by Balnexa, never logged and never echoed. Where a card must be told apart, only its last 4 digits are kept | `DELEGATED_DECISION` (2026-11-14), DRAFT until the Owner confirms | Real card statements print the full card number, for example in the payment slip. The SIN principle (the Owner decision of 2026-11-07: a SIN never enters Balnexa) carries over: the number has no use in the product, and storing it would add a breach liability. Until now the only card-number control was the 9006 CHECK on `account_identity_signal.masked_reference` (at most 4 digits) |

Scope: data that Balnexa stores in its database. An original statement kept as evidence in the household's data folder is the household's own copy, and its bytes are not changed. A future statement parser takes only the last 4 digits; the Python reference detector is ready for it.

## Detector v1.0.0

The reference implementation is `apps/executor/bnx_exec/pan_detector.py`. The database implementation is the `bnx.pan_*` functions in 9041.

1. Normalize with NFKC, so full-width digits become ASCII and a no-break space becomes a space.
2. Groups are maximal runs of ASCII digits. A group is **attached** if it touches an ASCII letter (hex digests, identifiers such as `a1234…`) or a decimal point or comma next to another digit (`0.3000…04`, `1234.50`). An attached group never counts. Letters are tested by code point, so the result never depends on the database collation.
3. A **candidate** is either a single free group of 13–19 digits, or consecutive free groups in one of the printed layouts 4-4-4-4, 4-4-4-4-3, 4-6-5 (Amex) or 4-6-4 (Diners), joined by exactly one space or hyphen.
4. A candidate is a PAN when it passes the Luhn check **and** its prefix and length match a scheme:

| Scheme | Prefixes | Lengths |
|---|---|---|
| Visa | 4 | 13, 16, 19 |
| Mastercard | 51–55, 2221–2720 | 16 |
| Amex | 34, 37 | 15 |
| Discover | 6011, 644–649, 65 | 16–19 |
| JCB | 3528–3589 | 16–19 |
| UnionPay | 62 | 16–19 |
| Diners | 300–305, 36, 38–39 | 14–19 |
| Debit (Maestro-type) | 50, 56–58, 63, 67 | 16–19 |

**Parity.** AT-PAN-02 compares the database implementation with the Python reference: 2,000 generated texts, with grouped, full-width, decimal and letter-adjacent cases, plus 400 JSON documents. Spans, masks, `has` and `mask_json` must all be identical. During development, five 3,000-text corpora also matched with no difference.

## Where it is enforced

| Point | Behaviour |
|---|---|
| `bnx.idem_begin` | Every command that stores data is refused with `PAN_CANDIDATE` when any key, string or number of its body holds a candidate. This includes the fields its audit entry leaves out (`register_evidence` name, `handoff_import` text) and the idempotency key |
| `bnx.audit` | The audited payload and subject are checked the same way. This covers the commands without idempotency, worker audits and installer audits |
| `bnx.stage_write` | `index_consumed` payloads are masked to the last 4 digits: an index record keeps `**** **** **** 1234`. Every other staging kind is refused |
| `tools/s4/pan_repo_scan.py` (CI, `secret-scan` job) | Tracked files and the whole history. A hit prints file, line and scheme, never the value. Published scheme test numbers are allowed by the SHA-256 of their digits (`pan_repo_scan_allow.txt`), so the allowlist holds no number. First run: 0 hits, and one published test number allowed (in an old evidence log) |

Refusals carry the command or staging kind as their detail. They never carry the value; AT-PAN-01 checks that no refusal echoes the number or its last 8 digits. The PWA shows `error.PAN_CANDIDATE` in English and Chinese: "enter only the last 4 digits; nothing was saved".

## Tests

- **AT-PAN-01** (core18) covers 12 paths, each refused with `PAN_CANDIDATE` and with nothing stored (plans, evidence files, ledger version, audit entries, staging):
  - plan item descriptions in the 4-4-4-4, Amex 4-6-5, full-width and single-run forms;
  - a draft description;
  - an evidence name;
  - a handoff text;
  - an idempotency key;
  - a JSON number;
  - a JSON object key;
  - a document-discovery result;
  - a direct audit subject.

  It also checks the index masking. Its control plan must pass and contains, among other things: a masked number, a 23-digit reference, a float, a SHA-256 digest of a card number, a UUID, a date, a phone number and "card ending 1234". The test fails without 9041.
- **AT-PAN-02** (core18): the parity check above.

## Limitations

| Id | Limitation |
|---|---|
| L-PAN-1 | **False positives are by design: the guard fails closed.** A random 16-digit reference has about a one-in-thirty chance of matching a scheme prefix and passing Luhn. Most transaction references are outside 13–19 digits. A refused command can be resent without the number |
| L-PAN-2 | A card number glued to other digits (one 26-digit run, as in some OCR scan lines) or to letters (`card4520…`) is not detected. Sliding windows inside long runs would flag many ordinary references. The statement parser must take only the last 4 digits whatever the layout |
| L-PAN-3 | Rows stored before 9041 are not rescanned. The synthetic instance holds only synthetic data; an instance that stored real data before 9041 would need a one-off scan |
| L-PAN-4 | Worker functions that write without `stage_write` or `audit` (usage records, capacity events, identity signals) are not scanned. They take fixed numeric fields from the Executor, and `masked_reference` keeps its 4-digit CHECK |
| L-PAN-5 | The Worker's guard for MCP tool responses scans for SINs only. A card number cannot be in a response unless it was stored, and the database refuses storing it |
